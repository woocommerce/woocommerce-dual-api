# Dual API engine tests

Unit tests for the engine: the hand-written code under `src/Internal/Api/` and `src/Api/Infrastructure/`, plus the resolver tree that `ApiBuilder` generates against a dummy code API kept under `Fixtures/DummyApi/`.

The tests run against the real WooCommerce test framework (`WC_Unit_Test_Case`, `WC_REST_Unit_Test_Case`, the `TestingContainer`), loaded from a WooCommerce checkout. See the [README](../../../../../README.md) at the repository root for how to set up the environment and run them.

## The dummy code API

`Fixtures/DummyApi/` is a hand-written code API (widgets and gadgets) that exercises every feature the builder supports: queries, mutations, output and input types, enums, interfaces, scalars, connections, custom attributes, granular authorization, metadata. `Fixtures/DummyApiAutogenerated/` is the tree the builder generates from it, and is committed.

Whenever the fixture changes, regenerate its generated tree and commit both:

```sh
composer build:api:test
```

`ApiBuilder` is not unit-tested directly; it is validated end to end through this fixture and the tests under `Autogenerated/`. When changing the builder or its templates, regenerate the fixture and treat a diff in the generated tree that isn't the change you intended as a signal to review.

`composer build:api:check` fails when the committed generated tree doesn't match the fixture's sources; CI runs it on every pull request.
